CRITICAL — WEBHOOK URL (MUST BE STABLE)
───────────────────────────────────────
  Stripe Dashboard → Developers → Webhooks → endpoint URL MUST be:

    https://YOUR-API-URL.vercel.app/webhooks/stripe

  NEVER point it at a preview URL like:
    https://sudo-xxxxx-sudospace.vercel.app/...

  Preview URLs die after deploys. If the webhook URL is wrong, payments
  succeed in Stripe but the database NEVER updates (subscription stays
  inactive). Events needed:
    • checkout.session.completed
    • customer.subscription.created
    • customer.subscription.updated
    • invoice.paid

  Automated update path (no manual DB edits):
    1. Stripe webhook → fulfillCheckoutSession → payment_sessions + subscriptions
    2. Device return from Checkout → POST /v1/payments/confirm (backup)
    Both write the same DB rows. UI then reads /v1/wallet/balance.

PHASE 3 — STRIPE CHECKOUT FLOW
═══════════════════════════════════════════════

1. User on Pi opens "Top up" → picks a pack ($5 / $10 / $25)

2. Pi calls your API:
   POST /v1/payments/checkout
   Authorization: Bearer <device_token>
   Body: { "price_id": "price_xxx_5" }

3. Backend:
   a. Creates payment_sessions row (status: pending)
   b. Creates Stripe Checkout Session:
      - mode: payment
      - line_items: [{ price: price_id, quantity: 1 }]
      - metadata: { session_id, device_id, user_id }
      - success_url: https://api.../v1/payments/success?session_id=...
      - cancel_url:  http://raspberrypi.local/#billing

4. Backend returns { checkout_url } → Pi redirects user to Stripe

5. User pays on Stripe-hosted page (you never touch card data)

═══════════════════════════════════════════════
PHASE 4 — WEBHOOK (MOST IMPORTANT PART)
═══════════════════════════════════════════════

Stripe sends events to:
  POST https://api.yourdomain.com/webhooks/stripe

Register in Dashboard → Developers → Webhooks → Add endpoint
Events to listen for:
  • checkout.session.completed
  • payment_intent.payment_failed   (optional)

Local testing:
  stripe listen --forward-to localhost:8000/webhooks/stripe
  # Copy whsec_... into STRIPE_WEBHOOK_SECRET

On checkout.session.completed:
  1. Verify webhook signature (stripe.Webhook.construct_event)
  2. Read metadata.session_id
  3. If payment_session already "paid" → return 200 (idempotent!)
  4. Mark payment_session paid
  5. Add USD credits to wallet (ledger entry)
  6. PATCH OpenRouter key limit for this device/user
  7. Return 200

NEVER trust the success_url alone — only the webhook confirms payment.

═══════════════════════════════════════════════
PHASE 5 — OPENROUTER KEY MANAGEMENT
═══════════════════════════════════════════════

Create a Management API key at:
  https://openrouter.ai/settings/management-keys

Per device (on first boot / pairing):
  POST https://openrouter.ai/api/v1/keys
  Authorization: Bearer <MANAGEMENT_KEY>
  Body: { "name": "sudo-device-abc123", "limit": 0 }

Store key_hash in DB. Give the plaintext sk-or-v1-... to the Pi agent
(once) or proxy inference through your API.

After top-up ($10 paid):
  PATCH https://openrouter.ai/api/v1/keys/{hash}
  Body: { "limit": <new_total_limit> }

Check remaining:
  GET https://openrouter.ai/api/v1/keys/{hash}
  → limit_remaining, usage

═══════════════════════════════════════════════
PHASE 6 — DEDUCT ON AI USAGE
═══════════════════════════════════════════════

Every OpenRouter response includes usage.cost (USD).

Option A — Pi/agent calls OpenRouter directly:
  After each request, POST /v1/usage/report to your API with cost.
  API deducts wallet + checks limit_remaining.

Option B — Proxy through cloud API (more control):
  Pi → POST /v1/chat → API → OpenRouter → deduct wallet → return response

Use DB transaction with row lock when deducting:
  SELECT balance FROM wallets WHERE user_id = X FOR UPDATE
